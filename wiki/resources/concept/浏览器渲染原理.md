# 浏览器渲染原理

本文基于 MDN 的《[[Populating the page how browsers work]]》（Web 性能指南）梳理浏览器从 URL 输入到页面可交互的**完整渲染管道**。与 [[Web 浏览器详解]]（浏览器基础定义与组件）互补，本文聚焦**性能关键路径**：导航 → 解析 → 渲染 → 交互。

> **核心洞见**：浏览器的渲染管道是**单线程、逐步推进**的流水线，每一个环节都可能成为性能瓶颈。理解这条管道是做好 Web 性能优化的前提。

## 导航（Navigation）

> 浏览器在发送真正的 HTTP 请求之前，需要完成 **DNS 查找 → TCP 三次握手 → TLS 协商**（HTTPS），共约 8 次往返。

### DNS 查找

- **目的**：将域名（如 `example.com`）解析为服务器 IP 地址。
- **过程**：浏览器 → DNS 解析器 → 各级域名服务器，逐级查询直到获得 IP。
- **缓存**：首次访问后 IP 被缓存在浏览器/OS/路由器等层级，后续请求跳过 DNS。
- **性能陷阱**：页面引用的**每个独立主机名**（字体 CDN、图片 CDN、广告网络、分析脚本等）都需要一次 DNS 查找。
- **移动网络**延迟更严重——DNS 请求需经过手机→基站→核心网→DNS 服务器。

### TCP 三次握手

三次握手（SYN → SYN-ACK → ACK）在浏览器与服务器之间建立可靠的 TCP 连接：
1. 浏览器发送 SYN 包
2. 服务器回复 SYN-ACK 包
3. 浏览器发送 ACK 确认

这三次往返在**真正发出 HTTP 请求之前**就已经发生。

### TLS 协商

HTTPS 连接额外需要 TLS 握手，协商加密算法、验证服务器证书、建立安全通道，**额外消耗 5 次往返**。

> **总和**：发送第一个 HTTP 请求之前，DNS + TCP + TLS ≈ 8 次往返。

## 响应（Response）

### TTFB（Time to First Byte）

浏览器发送 HTTP GET 请求后，服务器返回响应头 + HTML 内容。**TTFB** = 从用户发起请求（如点击链接）到收到**首个字节**的时间。

- 首批数据通常为 **14KB**，由 TCP slow start 机制决定。

### TCP Slow Start（拥塞控制）

TCP 将数据分割为**段（segment）**传输，通过**拥塞窗口（CWND）**控制传输速率：

| 阶段      | 行为                                   | CWND |
| ------- | ------------------------------------ | ---- |
| 初始      | 发送少量段（1/2/4/10 MSS，1 MSS = ~1500 字节） | 小    |
| 收到 ACK  | CWND **翻倍**，发送更多段                    | 指数增长 |
| 未收到 ACK | CWND **减半**，降低发送速率                   | 收缩   |

> **性能启示**：首批 14KB 是关键窗口——浏览器收到首批数据后立即开始解析。**将首屏渲染所需的 HTML + CSS 压缩到 14KB 以内**，可显著加速首次渲染。

## 解析（Parsing）

> 浏览器将收到的 HTML/CSS 字节流转为 **DOM** 和 **CSSOM** 两棵树，供渲染引擎使用。

### 关键渲染路径（Critical Rendering Path）

1. **构建 DOM 树**
2. **构建 CSSOM 树**
3. **合并为渲染树**（Render Tree）
4. **布局**（Layout / Reflow）
5. **绘制**（Paint）

### 构建 DOM 树

- HTML 解析包括**标记化（tokenization）**和**树构建**。
- `<html>` 是根节点，元素嵌套形成父子关系。
- DOM 节点越多，构建越慢。

**阻塞行为**：
| 资源类型 | 阻塞 HTML 解析 | 阻塞渲染 |
|----------|:---:|:---:|
| CSS | ❌ 不阻塞 | ✅ 阻塞渲染 |
| `<script>`（无 async/defer） | ✅ 阻塞 | ✅ 阻塞 |
| `<script async>` | ❌ | 可能阻塞 |
| `<script defer>` | ❌ | ❌（DOM 解析完后执行） |
| `<img>` | ❌ | ❌（异步加载） |

### 预加载扫描器（Preload Scanner）

> **关键优化机制**：DOM 构建占用主线程的同时，**预加载扫描器**在后台扫描 HTML，提前发起高优先级资源（CSS、JS、字体）的请求。

这意味着解析器遇到 `<link rel="stylesheet">` 时，CSS 文件可能**已经在下载中或已完成下载**，大幅减少阻塞时间。

**注意**：CSS 不阻塞 HTML 解析/下载，但**阻塞 JavaScript 执行**——因为 JS 常需查询 CSS 属性。

### 构建 CSSOM 树

- CSSOM 是 CSS 的对象模型，结构与 DOM 类似。
- 包含**用户代理样式表**（浏览器默认样式）。
- **级联（cascade）**：从最通用规则开始，逐层应用更具体的规则，递归计算每个节点的**最终计算样式**。
- CSSOM 构建**极快**——总时间通常**少于一次 DNS 查询**。

### JavaScript 编译

JS 文件下载后经历：**解析 → 编译 → 解释执行**。脚本被解析为**抽象语法树（AST）**，部分引擎将 AST 编译为字节码。**大部分 JS 在主线程执行**（Web Worker 除外）。

### 无障碍树（AOM）

浏览器同时构建**无障碍对象模型（AOM）**，是 DOM 的语义版本，供屏幕阅读器等辅助技术使用。AOM 随 DOM 更新而更新。**在 AOM 构建完成前，内容对屏幕阅读器不可访问**。

## 渲染（Render）

> 渲染 = **样式（Style）→ 布局（Layout）→ 绘制（Paint）→ 合成（Compositing）**

### Style（样式 / 渲染树构建）

合并 DOM 和 CSSOM → **渲染树（Render Tree）**：
- 遍历 DOM 的每个**可见节点**。
- `<head>` 及其子元素、`display: none` 的节点**不进入渲染树**。
- `visibility: hidden` 的元素**仍占位**，进入渲染树。
- 每个可见节点应用对应的 CSSOM 规则，求**计算样式（computed styles）**。

### Layout（布局 / 回流）

计算渲染树中每个节点的**精确尺寸和位置**：
- 浏览器从渲染树根节点开始遍历。
- 以**视口大小**为基础，自顶向下计算每个盒子的几何属性。
- 每个元素按**盒模型（box model）**确定宽高、内边距、边框、外边距。
- 首次计算叫 **Layout**；后续重新计算叫 **Reflow（回流）**。

> **性能关键**：只要修改影响布局的 CSS 属性（width/height/margin/padding/border/top/left 等），就会触发 Reflow，这是一个**昂贵的全量或局部重算过程**。

### Paint（绘制 / 光栅化）

将布局阶段计算的盒子转换为屏幕上的**实际像素**：
- 绘制文字、颜色、边框、阴影、按钮、图片等每个视觉元素。
- 通常将页面分解为**多个图层（layers）**以加速后续重绘。
- **60fps 目标**：主线程的样式计算 + 回流 + 绘制必须在 **16.67ms** 内完成。

**GPU 图层提升（Layer Promotion）**：
以下属性/元素会创建独立的 GPU 合成层（在 GPU 而非 CPU 主线程上绘制）：

| 触发条件 | 示例 |
|----------|------|
| CSS 属性 | `opacity`、3D `transform`、`will-change`、`filter` |
| 特定元素 | `<video>`、`<canvas>` |

> **注意**：图层提升性能但消耗 GPU 内存，**不应过度使用**。

### Compositing（合成）

当页面元素分布在不同图层时，合成步骤将图层**按正确顺序叠加**，确保渲染正确。

**触发链**：Reflow → Repaint → Re-composite。如果定义了图片尺寸（width/height），图片加载后只需重绘该图层并合成，无需回流。

## 交互性（Interactivity）

### TTI（Time to Interactive）

> **TTI** = 从首次请求到页面在 **50ms 内响应**用户交互的时间点。

即使页面"看起来"已渲染完毕，JavaScript 可能仍在占用主线程：
- **下载** → **解析** → **编译** → **执
- 行** JS 期间，主线程**无法响应**滚动、点击、触摸。
- 延迟加载（defer）的 JS 在 `onload` 事件后执行，此时主线程可能仍忙碌。
- 大型 JS 文件（如 2MB）在慢网络下会导致长时间无响应（**jank**）。

> **性能目标**：保持主线程空闲，能够随时处理用户交互。避免长任务（>50ms）阻塞主线程。

## 性能优化要点总结

| 阶段 | 优化策略 |
|------|----------|
| **导航** | 减少主机名数量（减少 DNS 查询）；使用 CDN 降低延迟；预连接（`<link rel="preconnect">`） |
| **响应** | 首 14KB 包含首屏 HTML + 内联 CSS；启用压缩（gzip/brotli） |
| **解析** | 脚本用 `async`/`defer`；关键 CSS 内联；减少 DOM 深度 |
| **渲染** | 避免触发布局的 CSS 变更；用 `transform`/`opacity` 做动画（GPU 合成）；指定图片尺寸避免回流 |
| **交互** | 代码拆分（code splitting）；延迟加载非关键 JS；控制 JS 包大小 |
