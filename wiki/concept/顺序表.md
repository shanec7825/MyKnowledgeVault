# 顺序表（动态数组）

## 核心思想

**用一段连续内存保存线性表的元素。**

三个必要字段：

```
data:     [10, 20, 30, 40, _, _, _, _]
size     = 4      // 逻辑长度（有效元素个数）
capacity = 8      // 物理容量（已申请的内存槽位数）
```

`size ≤ capacity` 恒成立。**`size` 是逻辑概念，`capacity` 是物理概念**——两者混用是初学阶段最常见的 bug 来源（用 `size` 当循环上界去访问已申请内存，或用 `capacity` 当元素个数去遍历）。

它是几乎所有语言里的默认「列表」实现：C++ `std::vector`、Java `ArrayList`、Python `list`、C# `List<T>`。

## 为什么 get/set 是 O(1)：地址计算

连续内存 ⇒ 第 i 个元素的地址可以直接算出来，不需要从头遍历：

```
address(i) = base + i * sizeof(T)
```

这是「随机访问」的全部含义，也是**数组下标从 0 开始**的原因——从 0 起算，地址公式里少一次减法；从 1 起算就要写成 `base + (i-1) * size`。代价是一个减法，收益是一个更简洁的公式（以及早期编译器少一条指令）。

推论：这个公式成立的**前提是元素定长且内存连续**。一旦元素变长（变长字符串）或内存不连续（链表），O(1) 随机访问立刻失效。

## 复杂度总表

| 操作 | 复杂度 | 原因 |
| --- | --- | --- |
| `get(i)` | **O(1)** | 直接地址计算 |
| `set(i, e)` | **O(1)** | 直接地址计算 |
| `search(e)` | O(n) | 必须逐个比较（无序表） |
| `insert(i, e)` | **O(n)** | i 之后的元素全部后移一格 |
| `remove(i)` | **O(n)** | i 之后的元素全部前移一格 |
| `append(e)` | **摊还 O(1)** | 多数情况直接放；偶尔触发扩容整体复制 |
| `traverse()` | O(n) | 每个元素访问一次 |

**注意 `insert` / `remove` 的 O(n) 与 i 有关**：头部插入要搬 n 个元素，尾部插入搬 0 个（`append` 除外，它可能触发扩容）。教材写 O(n) 是最坏情况，不是每次都是 n。

## 扩容：代价从哪来

容量固定 ⇒ 满了必须换一块更大的内存，把旧元素复制过去（`new` + 逐个赋值 + `delete[]`）。扩容因子决定代价：

- **每次 +1**：n 次追加的总搬运次数 ≈ 1+2+…+n = O(n²)。**灾难**。
- **每次 ×2**：总搬运 < 2n = O(n)，摊还到每次是 O(1)。但容量最多浪费近 50%。
- **每次 ×1.5**：总搬运仍是 O(n)（约 3n），内存浪费更少，但复制更频繁。多数工程库在 1.5 与 2 之间取。

**结论：扩容因子必须 > 1 且成倍增长，摊还 O(1) 才成立。** 严格证明见 [[摊还分析]]。

## 缩容：同样是权衡

删除元素后不缩容 ⇒ 内存长期浪费；缩容太积极 ⇒ **抖动**（shrink 后立刻 insert 又触发 grow）。

常见策略：**当 `size < capacity / 4` 时，缩到 `capacity / 2`**，并设一个容量下限（如 8）。选 1/4 而不是 1/2 的原因：留出缓冲带，避免「删一个缩容、插一个扩容」的反复复制。缩容的摊还代价分析方式与扩容相同（同样是指数式的容量变化）。

## 优缺点

**优势**

- 随机访问 O(1)——按下标取值是常数时间。
- **缓存友好**——连续内存意味着一次 cache line 加载能带出多个元素，遍历的实际速度远超链表（这是链表在实际 benchmark 中经常输给顺序表的主要原因）。
- 尾部追加摊还 O(1)，无额外指针开销，空间利用率高。

**劣势**

- 插入 / 删除要搬移元素，中间位置最坏 O(n)。
- 需要**一整块连续内存**，大对象 + 内存碎片时可能申请失败。
- **扩容会导致指针 / 引用 / 迭代器失效**——它们指向的是旧内存块，不是「数据本身」。
- 容量预留造成空间浪费（最多近一倍）。
