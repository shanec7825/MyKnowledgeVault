## 第 1 章 从源文件到可执行文件：构建流水线

> [!question] 自学提问（先想 30 秒再往下读）
> gcc main.c -o a.out 这一条命令背后，实际发生了几个步骤？如果我在 Windows 上用 gcc，产物 a.out 能拿到没有安装编译器的电脑上直接双击运行吗？

### 1.1 四步流水线：每一步的输入和输出

编译器不是一个黑盒，而是四道工序的流水线。gcc 用不同的选项让你「停在」任意一道工序，这正是本实验的观察点：

```text
第①步 预处理  cpp   main.c  →  main.i
  · 以 # 开头的行在这里被处理：#include 把文件原样粘贴进来
  · #define 宏被替换成字面文本；#ifdef 条件决定哪些行保留
  · 产物 main.i 仍然是 C 文本，只是「又长又啰嗦」
  · 观察命令：gcc -E main.c -o main.i

第②步 编译    cc1   main.i  →  main.s
  · 把 C 翻译成汇编（针对 x86-64 就是 x86-64 汇编）
  · 产物 main.s 是给人看的文本，每行大致对应一条机器指令
  · 观察命令：gcc -S main.c -o main.s     （不加 -S 会一路走完）

第③步 汇编    as    main.s  →  main.o
  · 把汇编翻译成机器码（二进制），产物 main.o 是「目标文件」
  · 此时函数/全局变量的地址还是占位符，等待第④步确定
  · 观察命令：gcc -c main.c -o main.o

第④步 链接    ld    main.o + 别的.o + 库  →  a.out
  · 把多个目标文件和库拼成一个可执行文件，确定最终地址
  · 只有一个 main.c 也要链接：启动代码、printf 所在的库都在这一步并入
  · 观察命令：gcc main.c -o a.out         （不加 -c/-S 就会走完链接）
```

### 1.2 动手实验：五步流水线

建一个最小项目（文件名建议就叫 main.c）：

```c
// main.c —— 项目 0 的最小观察对象
#include <stdio.h>

int add(int a, int b) {     // 自己写的函数：观察它的汇编
    return a + b;
}

int main(void) {
    int x = 3, y = 4;
    printf("add(3,4) = %d\n", add(x, y));   // 调用库函数 printf
    return 0;
}
```

依次执行并保存每一步的输出（存档是提交物的一部分）：

```bash
gcc -E main.c -o main.i        # ① 预处理
wc -l main.c main.i            # 对比行数：main.i 通常暴涨到几百行
gcc -S main.c -o main.s        # ② 编译
cat main.s                     # 看汇编文本（找 <add> 或 add:）
gcc -c main.c -o main.o        # ③ 汇编
file main.o                    # 应显示 ELF 64-bit relocatable（可重定位）
gcc main.c -o a.out            # ④ 链接
file a.out                     # 应显示 ELF 64-bit executable（可执行）
./a.out                        # ⑤ 执行
ls -l main.c main.i main.s main.o a.out   # 记录每个产物的大小
```

> [!tip] 先预测再运行
> 跑 wc -l 之前先写下：你预计 main.i 有多少行？比 main.c 多还是少？为什么？跑完再对照。预测里写清「依据」——比如「#include 会把整个 stdio.h 粘进来」。

### 1.3 为什么需要四步？理解分工

- 预处理解决「文本拼接」：让多个文件共享声明（声明的细节见项目 4 链接）。
- 编译解决「语言翻译」：C 是给人写的，CPU 只认机器码，汇编是中间的可读形态。
- 汇编解决「编码」：把助记符（add、mov）变成 0/1 字节。
- 链接解决「拼装与地址」：你的代码要用 printf，但 printf 的实现不在你的文件里；链接器把它们合到一起并确定最终地址。

**一句话记忆：**

```text
预处理拼文本 → 编译变汇编 → 汇编变机器码 → 链接定地址、合全局
```

### 1.4 环境说明（Linux / WSL）

大纲建议使用 Linux 或 WSL（Windows 上的 Linux 子系统）。检查环境：

```bash
uname -a          # 看内核与架构（应出现 x86_64 / GNU/Linux）
gcc --version     # 确认 gcc 可用
which gdb objdump strace   # 确认观察工具齐全（缺了用 sudo apt install gdb binutils strace）
```

如果你用 WSL：文件建议放在 Linux 文件系统内（如 ~/project0）而不是 /mnt/c/...，这样文件权限与执行行为与真实 Linux 一致，不会出现「有 x 权限却跑不起来」的怪现象。

> [!tip] 到这台机器上怎么做
> 本章的实验在本机（Windows + WSL2 / Ubuntu 24.04）的具体落地步骤、实测输出与常见报错，见 [[自学文档0（补）-WSL 实操衔接手册]]：包括如何进入 WSL、装 strace、`~/project0` 的搭建、`gcc` 四步流水线在 Ubuntu 24.04 下与本文档示例的差异（默认 PIE，地址为 0x1149 而非 0x401126），以及把输出直接存进本库的证据目录。

## 第 2 章 四个关键对象：源文件、目标文件、可执行文件、进程

> [!question] 自学提问（先想 30 秒再往下读）
> main.o 和 a.out 都是二进制文件，为什么 main.o 不能直接运行？「程序」和「进程」只差一个字，差在哪里？

### 2.1 一句话定义

| **对象** | **是什么** | **谁的产物** | **状态** |
| --- | --- | --- | --- |
| 源文件 main.c | 你写的 C 文本，人可读 | 编辑器 | 磁盘上的静态文本 |
| 目标文件 main.o | 机器码 + 符号表，但地址未定（可重定位） | 汇编器 as（gcc -c） | 磁盘上的静态二进制 |
| 可执行文件 a.out | 机器码 + 确定的地址 + 启动代码 + 库 | 链接器 ld（gcc） | 磁盘上的静态二进制 |
| 进程 | 可执行文件被内核装入内存后的「运行实例」 | 内核（./a.out） | 内存中的动态存在 |

```text
进程 = 可执行文件 + 内核分配的运行资源
                │                    │
                │                    ├─ PID（进程编号）
                │                    ├─ 虚拟内存（代码、数据、栈、堆）
                │                    ├─ 打开的文件描述符
                │                    └─ 寄存器现场、调度状态
                └─ 磁盘上那份字节的「内存副本」
```

所以：可执行文件是「菜谱」，进程是「正在做的那道菜」。同一个 a.out 可以同时跑出多个进程（各自有各自的 PID、内存、变量）。

### 2.2 动手实验：给四种对象「拍证件照」

```bash
# 1) 看类型
file main.c main.i main.s main.o a.out

# 2) 看符号（函数名、全局变量名）
objdump -t main.o     # 目标文件符号表：add、main… 地址多为 0
objdump -t a.out      # 可执行文件符号表：地址已是真实地址

# 3) 看节（section）布局：代码、数据各住在哪里
objdump -h main.o
objdump -h a.out

# 4) 看「运行起来」的进程：另开一个终端
./a.out &             # 放后台（若程序瞬间结束，可换成 sleep 100 的版本）
ps -ef | grep a.out   # 找到 PID
ls -l /proc/<PID>/exe     # 内核记录它运行的是哪个可执行文件
ls /proc/<PID>/           # 进程的全部身份信息
```

> [!tip] 证据要点
> objdump -t 的对比是本章核心证据：同一个 add 函数，在 main.o 里地址栏是 0（还没定），在 a.out 里是真实地址（链接时定好）。把这两段输出并排贴进你的观察记录。

### 2.3 常见误区

- 「双击 a.out 没反应 / 报不是可执行文件」——不是文件坏了，而是要么缺 x 权限（chmod +x a.out），要么这是目标文件 main.o 被误当成程序。
- 「file 显示 ELF relocatable」= 目标文件，「ELF executable」= 可执行文件。relocate（重定位）就是「地址还没定、等着被安放」的意思。
- 「进程结束就没了」——进程是临时的，a.out 永远躺在磁盘上。重启电脑进程全没，文件还在。

## 第 3 章 机器指令初见：objdump 反汇编

> [!question] 自学提问（先想 30 秒再往下读）
> C 里的 add(x, y) 一行，到机器层面变成了几条指令？返回值 3+4=7 放在哪里交还给调用者？

### 3.1 反汇编在看什么

汇编是机器码的「可读翻译」。objdump -d 把可执行文件拆回汇编，让你看到 C 代码的「真身」。项目 0 只要求能认出三样东西：函数入口、参数、返回值——不要求精通汇编（那是项目 2 的事）。

```asm
$ objdump -d a.out | grep -A 20 "<add>:"
0000000000401126 <add>:
  401126: 55                    push   %rbp
  401127: 48 89 e5              mov    %rsp,%rbp
  40112a: 89 7d fc              mov    %edi,-0x4(%rbp)   # 参数1 存到栈
  40112d: 89 75 f8              mov    %esi,-0x8(%rbp)   # 参数2 存到栈
  401130: 8b 55 f8              mov    -0x8(%rbp),%edx
  401133: 8b 45 fc              mov    -0x4(%rbp),%eax
  401136: 01 d0                 add    %edx,%eax         # 真正的加法！
  401138: 5d                    pop    %rbp
  401139: c3                    ret                     # 返回值在 %eax
```

读法（三条就够）：

- 第一列是地址，第二列是机器码字节，第三列开始是汇编助记符。
- % 开头的是寄存器：%rdi、%rsi 放前两个参数；%rax 放返回值（x86-64 约定）。完整的调用约定见项目 2，这里先记住「参数进 %rdi/%rsi，返回值出 %eax」。
- add %edx,%eax 就是 a+b 本身；其余多是「把参数搬来搬去」的记账动作。

### 3.2 动手实验

```bash
objdump -d a.out > asm.txt          # 保存全部反汇编
grep -n "<add>:" asm.txt            # 定位 add 函数
grep -n "<main>:" asm.txt           # 定位 main 函数
# 找出调用 printf 的 call 指令：
grep -n "call" asm.txt
```

练习（写进观察记录）：

1. 在 add 的汇编里圈出「真正做加法」的那条指令。
1. 找到 main 里 call add 之前把 3、4 装进寄存器/栈的指令。
1. 找到 call printf 对应的指令，看看它的地址和 add 的地址有什么不同（提示：plt）。

> [!info] 不用慌
> 第一次看汇编「看不懂 80%」是正常的。项目 0 的目标只是：能在一堆指令里认出函数入口、call 调用、加法指令、ret 返回。剩下的留到项目 2。

## 第 4 章 运行时观察：gdb 调试器

> [!question] 自学提问（先想 30 秒再往下读）
> 在 add 的第一行设断点，程序停下时：x 和 y 的值是多少？它们存在寄存器里还是内存里？你怎么证明？

### 4.1 gdb 是什么

前面的 objdump 看的是「磁盘上的静态文件」；gdb 看的是「内存里正在跑的进程」。它可以让程序停下、单步走、查看变量和寄存器——就像给程序装了暂停键和透视镜。

### 4.2 最小命令集（先背这 8 条）

| **命令** | **作用** | **类比** |
| --- | --- | --- |
| gdb ./a.out | 启动调试（必须带 -g 编译） | 把程序放上手术台 |
| break add | 在 add 函数入口设断点 | 设路障 |
| run | 开始运行，直到断点停下 | 按下播放键 |
| next（n） | 执行下一行，不进入函数 | 单步跨过 |
| step（s） | 执行下一行，进入函数内部 | 单步跨入 |
| print x（p x） | 显示变量/表达式的值 | 伸手量一量 |
| info registers | 显示所有寄存器 | 看仪表盘 |
| backtrace（bt） | 显示调用栈：谁调用了谁 | 看现场的「来龙去脉」 |
| continue（c） | 继续跑到下一个断点/结束 | 继续播放 |
| quit（q） | 退出 gdb | 下手术台 |

### 4.3 动手实验：给 add 设断点

```bash
# 1) 用调试信息 + 不优化 编译（两个条件缺一不可）
gcc -g -O0 main.c -o a.out

# 2) 启动调试
gdb ./a.out
(gdb) break add        # 断点 1：add 入口
(gdb) run               # 运行，停在 add
(gdb) info args         # 看参数 a、b 的值（应为 3、4）
(gdb) info locals       # 看局部变量
(gdb) info registers rdi rsi rax    # 看参数寄存器
(gdb) next              # 执行 return a + b
(gdb) info registers rax           # 看返回值（应为 7）
(gdb) backtrace         # 看是谁调用了 add（应为 main）
(gdb) continue          # 继续跑完
(gdb) quit
```

> [!tip] 必须先写下的预测
> run 之前回答三问：① 断点停下时 a、b 各是多少？② 返回值会出现在哪个寄存器？③ backtrace 里会出现几层调用？把答案写在纸上，再动手验证。

### 4.4 常见问题

| **现象** | **原因** | **解决** |
| --- | --- | --- |
| gdb 显示 <no symbolic name> / 无法打印变量 | 编译时没加 -g，或加了 -O2 变量被优化掉 | 用 gcc -g -O0 重新编译 |
| 断点不生效 | 函数被内联/优化，或名字打错 | 用 -O0；用 break 文件名:行号 |
| run 之后直接结束，没停 | 断点设在了没被执行到的路径上 | 确认代码真的调用了 add |
| 变量显示 <optimized out> | 优化把变量「消掉了」 | -O0 编译；理解为「变量不一定在内存」 |

**最后一个现象值得多想一层：**

变量可能在寄存器里、可能在内存栈上、也可能被优化得「不存在」。这是大纲验收点「知道变量可能位于寄存器、内存或被优化掉」的由来——观察记录里必须注明编译条件（-g -O0 还是 -O2），否则结论不成立。

## 第 5 章 与内核对话：strace 与 /proc

> [!question] 自学提问（先想 30 秒再往下读）
> 程序第一次执行 printf 时，字符串去了哪里？是谁真正把它显示到屏幕上的——你的程序，还是内核？

### 5.1 两种观察：系统调用轨迹 与 进程身份

你的程序运行在「用户态」，它自己不能直接操作屏幕、磁盘、网络。每当需要这些服务，它就发出「系统调用」请求内核代劳。strace 记录这些请求；/proc 是内核为每个进程建立的「档案柜」。

```c
用户态程序                     内核
   printf("hello\n")           │
        │                       │
        │ ① 用户态库里攒够一行   │
        ├──────────────────────►│ ② write(fd=1, "hello\n", 6) 系统调用
        │◄──────────────────────┤ ③ 内核把字符送到终端
        │      返回写入字节数     │
```

### 5.2 strace：看程序向内核要了什么

```bash
$ strace ./a.out
execve("./a.out", [...], [...])        = 0        ← 内核装入程序
brk(NULL)                              = 0x...    ← 申请堆内存
openat(AT_FDCWD, "/etc/ld.so.cache",…) = 3        ← 找动态库
write(1, "add(3,4) = 7\n", 13)         = 13       ← 打印那一行！
exit_group(0)                          = ?        ← 进程结束

# 常用变体：
strace -c ./a.out      # 汇总：每种系统调用出现了几次、占多少时间
strace -f ./a.out      # 连子进程一起跟（项目 6 用得上）
strace -e write ./a.out  # 只看 write
```

读法：每行左边是「调用名(参数)」，右边是内核的返回值。返回 -1 或错误码表示失败。重点观察三件事：

1. printf 对应的是 write(1, ...) ——1 是标准输出（屏幕）的文件描述符。
1. 程序启动和退出各发生了什么调用（execve 进来，exit_group 出去）。
1. 如果你的程序没有输入输出，系统调用会非常少——「纯计算几乎不打扰内核」。

### 5.3 /proc：内核的进程档案柜

```c
# 先让进程「活着」（改一行：在 return 0; 前加 sleep(30); 或另开终端跑 sleep 100）
$ ./a.out &
$ ps -ef | grep a.out        # 记下 PID，比如 12345

cat /proc/12345/status       # 身份：名字、PID、PPID（父进程）、状态、内存
ls -l /proc/12345/fd         # 打开的文件：0 输入 1 输出 2 错误
cat /proc/12345/maps         # 内存映射：代码、库、栈、堆各在哪个地址段
readlink /proc/12345/exe     # 这个进程运行的是哪个可执行文件
```

> [!info] 对应大纲验收点
> 「解释源文件、目标文件、可执行文件与进程的区别」+「说明 gdb、objdump、strace、/proc 各自提供什么证据」。自查口诀：objdump 看文件、gdb 看运行、strace 看请求、/proc 看身份。

### 6.5 可选拓展：调试信息与优化级别

大纲的可选拓展：比较带调试信息和不同优化级别的构建结果。做法：

```bash
gcc -g -O0 main.c -o a_O0      # 无优化 + 调试信息
gcc -g -O2 main.c -o a_O2      # 高优化 + 调试信息
gcc    -O2 main.c -o a_O2s     # 高优化、无调试信息

ls -l a_O0 a_O2 a_O2s          # 比大小
objdump -d a_O0 | grep -A 15 "<add>:"   # 无优化的 add
objdump -d a_O2 | grep -A 15 "<add>:"   # 优化后的 add：可能整个函数消失（被内联）！
gdb ./a_O2   →  break add → run → print x   # 可能报 optimized out
```

预期现象（先预测再验证）：-O2 的文件更小、指令更少、add 可能被内联消失、gdb 里变量不可见。结论雏形：优化让代码更快，但让「源码 ↔ 机器码」的对应关系变模糊——这就是项目 2、项目 5 的伏笔。

## 附录 A 自测题（答案在后面，先做）

1. gcc -c 和 gcc（不带 -c）分别产出什么？后者多了哪一步？
1. 为什么说 main.o 是「可重定位」文件？重定位在什么时候完成？
1. 进程和可执行文件的关系，用一个类比说明。
1. objdump -t main.o 里 add 的地址栏为什么是 0？链接后变成什么？
1. printf 最终通过哪个系统调用输出文字？strace 里怎么认出它？
1. gdb 中 next 和 step 的区别？什么情况下必须用 step？
1. 为什么用 gdb 观察变量必须加 -g -O0？只加 -g 行不行？
1. /proc/PID/maps 能回答什么问题？它证明了什么、不能证明什么？
1. strace 显示 write(1, ...) = 13，这个 13 是什么？如果返回 -1 又说明什么？
1. 把 a.out 复制到另一台装有相同架构 Linux 的电脑，能直接 ./a.out 运行吗？什么情况下不能？

**参考答案：**

1) -c 只产出目标文件 main.o（汇编步之后就停）；不带 -c 会继续链接，产出可执行文件 a.out。2) 因为其中的地址是占位符，要等链接器把多个目标文件合并时统一确定最终地址。3) 可执行文件是菜谱，进程是正在做的菜；进程 = 文件内容 + 内核分配的 PID、内存、寄存器、文件描述符。4) 目标文件里地址未定（可重定位）；链接后变为最终虚拟地址。5) write 系统调用，第一个参数是 1（标准输出）；认法：write(1, "…", 长度)。6) next 不进入函数，step 会进入；想观察被调用函数内部时用 step。7) -g 生成调试信息（变量名/行号），-O0 禁止优化防止变量被优化掉；只加 -g 而用 -O2 仍可能看不到变量。8) 进程各内存段的地址范围（代码、库、栈、堆）；它能证明映射存在，不能单独证明地址翻译机制（虚拟内存见项目 7）。9) 13 是成功写入的字节数；-1 表示失败，具体原因看 errno（如重定向到只读文件）。10) 一般能运行（同为 x86-64 且动态库兼容）；动态链接依赖目标机器上有对应共享库，缺库会失败（项目 4 展开）。

### 附录 B 一页速记

```bash
四步流水线：预处理拼文本 → 编译变汇编 → 汇编变机器码 → 链接定地址
四个对象：  源文件(文本) → 目标文件(机器码,地址未定) → 可执行文件(地址已定) → 进程(文件+内核资源)
四大工具：  objdump 看文件 | gdb 看运行 | strace 看请求 | /proc 看身份
必加选项：  gcc -g -O0  （调试必带）；-Wall 常开；2>&1 存全输出

```
